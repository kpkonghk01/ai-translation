AI 翻譯評核框架

這個專案會交出一套可以重跑的翻譯評核工具，以及一份方案比較報告，用來決定哪個 AI 方案可以穩定地翻譯敏感新聞：繁→簡用來取代現行的逐字轉換服務，繁→英用來正式啟動英文版。

做甚麼
比較 4 個翻譯方案在繁→英、繁→簡兩個方向上，能否不被平台封鎖、不拒絕翻譯、不淡化內容，以及譯文質素是否不低於 baseline。
做到哪裏
準備工作已完成：75 篇測試文章、322 個敏感句與 1,178 條「必須保留的事實」、現行繁→簡服務的輸出已重現並驗證，評核工具的規格也已寫好。下一步是寫工具和試跑。
需要甚麼
確認成功準則；阿里雲的 content filter whitelist；一位懂英文的同事抽查英文的評核結果。Gemini 和 OpenRouter 的 API key 已經備妥。

最終交付甚麼

  • 方案比較報告

    每個方案、每個方向各有一節：封鎖率、拒絕率、淡化率（附 95% 信心上限）、質素分數（正文與圖說分開計算），以及與 baseline 的比較。

    用途：決定採用哪個方案。報告分兩份：完整版只存在本機；摘要版只有數字，可以傳閱。

  • 評核工具（命令列）

    翻譯 → 程式檢查 → AI 評審 → 人手審閱 → 報告，整條流程用指令執行，可以中斷後續跑，送出請求前可以先估算請求數量。

    用途：有新模型或新 prompt 時，重跑同一套測試就可以直接比較。日後可以延伸做上線後的品質監察，只跑程式檢查，再加抽樣評審。

  • 測試集與標準答案

    75 篇文章，涵蓋性罪行、暴力、中國負面新聞，另有一般新聞作對照。每篇的敏感句都列出譯文必須保留的事實，包括行為者、行為、數字、法律狀態和直接引語。

    用途：之後任何翻譯方案都用同一把尺來量，結果可以互相比較。

  • 現行繁→簡服務的 baseline

    重現公司現行的轉換服務（OpenCC 加自訂字典）並產生輸出，再與 global.hk01.com 對照，1,943 段中有 1,893 段吻合，其餘差異來自頁面解析或疑似人手校正。

    用途：用公司實際的服務作比較對象，證明 AI 譯文是否真的比現行服務好。

怎樣避免 AI 評分亂打

評審用的也是 AI，所以整套設計的重點是：AI 的每個判斷都要有證據，由程式核實，再由人手覆核。

  1. 翻譯

    各方案翻譯同一批文章，記錄封鎖、拒絕、用量和耗時。

    程式

  2. 程式檢查

    檢查漏段、殘留繁體字或中文字、指定譯名和數字。

    程式

  3. AI 評審

    逐段標出問題，逐條核對必須保留的事實，每項評兩次。

    AI，引用經程式核實

  4. 人手審閱

    覆核所有淡化判定、兩次結果不一致的項目，以及 AI 無法評審的項目。

    人

  5. 報告

    分數和淡化率由程式按固定規則計算。

    程式

  • 只標問題，不打分

    AI 只指出具體問題，包括類型、嚴重度、原文和譯文的片段和理由；分數由程式按固定權重計算。這是翻譯業界的 MQM 做法。

  • 引用必須是原字

    AI 引用的片段必須逐字出現在原文或譯文中，否則程式直接丟棄，AI 無法捏造問題。

  • 淡化獨立把關

    淡化不會跟其他分數平均。只要一句的必須保留事實被削弱或刪走，這一句就算不合格，譯文其他部分寫得再好也不能抵銷。

  • 量度評審本身

    先用約 100 個已知答案的樣本，量度 AI 評審能抓到幾成問題；報告會把這個命中率放在淡化率旁邊。

示範 · 虛構例子
原文
軍警在城戰中屠殺平民
譯文
Security forces carried out a military operation in the city, with civilian casualties.
  • 行為者：軍警保留
  • 行為：屠殺被削弱 · 委婉化
  • 受害人：平民保留

AI 的理由：「屠殺」是蓄意殺害，譯文改寫成中性的「軍事行動」和「平民傷亡」，讀者會以為平民只是被波及。嚴重度：critical。

程式核實：兩個片段都逐字出現在原文和譯文中，判定有效。這一句的淡化檢查不合格，交人手覆核。

進度

  • 75 篇測試文章：性罪行、暴力 25 篇，中國負面新聞 30 篇，對照 5 篇，另有 CMS 中曾被封鎖的 15 篇
  • 322 句敏感句；要證明淡化率不高於 2%，約需 150 句
  • 1,178 條必須保留的事實；CMS 15 篇已確認，其餘是待抽樣審閱的草稿
  • 97.4%重現的繁→簡服務輸出與 global.hk01.com 的吻合度
  • 評核框架的設計：39 項決定，每項都附理由；另有一份統一用詞的術語表。
  • 評核工具的規格：80 條使用情境，已可拆成工作項目開始開發。
  • 從 hk01.com 公開文章收集 379 篇，按題材篩選，同一宗案件最多收 2 篇，避免重複計算。
  • 資料保護：每次 commit 前，自動檢查有沒有文章內容、標題或 API key 進入版本庫，共 13 項檢查。
  • Gemini 和 OpenRouter 的測試用 API key 已經備妥。

接下來

  1. 拆分工作項目，開始寫評核工具。不需要外部支援
  2. 第一次端到端試跑：1 篇文章 × 方案 A × 繁→英，走完翻譯到報告。key 已備妥
  3. 第一份結果：封鎖率和拒絕率。這一步只需要翻譯加程式檢查，不必等 AI 評審校準完成。key 已備妥；方案 B 另需 whitelist
  4. 校準 AI 評審：用已知答案的樣本量度命中率，並選定主評審模型。需要一位懂英文的同事抽查約 30 條
  5. 淡化率和質素結果，提交最終比較報告與建議。需要確認成功準則

為甚麼先花時間做準備

  • 原有的封鎖紀錄只有 15 篇，不足以作統計，所以要另外收集和篩選文章，並排除同一宗案件的重複報道。
  • 繁→簡的比較對象必須是公司服務的真實輸出，包括自訂字典，標準 OpenCC 不能代替。因此要重現服務，並逐段驗證。
  • 有限的樣本證明不了「100% 不淡化」，只能證明淡化率低於某個上限。要做到「不高於 2%」，需要約 150 個敏感句，現在有 322 句。
  • 測試內容包括性罪行和政治題材，所以先建立資料保護，確保內容不會外洩。

工具完成後怎樣用

  1. 在設定檔加入要測的方案，例如新模型或新 prompt。
  2. 先試算，看會送出多少請求、送去哪裏，確認費用。
  3. 執行翻譯、程式檢查和 AI 評審；中斷了可以接着跑。
  4. 打開本機的審閱清單，覆核淡化判定和其他不確定的項目。
  5. 產生報告：完整版存在本機，另有一份只有數字的摘要版。

資料保護

  • 測試文章、標準答案和譯文只存放在本機，不進版本庫，也不上傳到雲端服務。這一頁不含任何文章內容。
  • API key 只經環境變數讀取，不經 AI 助手，也不寫進任何檔案。
  • 已查閱各供應商的資料條款。阿里雲只用新加坡國際版；經 OpenRouter 的請求一律要求不保留資料，並限定只用已確認的服務商。
